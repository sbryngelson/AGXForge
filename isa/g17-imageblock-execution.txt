# THE IMAGEBLOCK HOLDS DATA, IT IS INDEXED BY THE THREAD POSITION, AND APPLE EMITS NO BARRIER.
# All three measured with tools/g17ibrun on an unpatched, xcrun-metal-compiled kernel.
#
#   struct IBS { half4 c; float d; uint k; ushort s; uchar b; };
#   kernel void k(imageblock<IBS, imageblock_layout_explicit> ib, device uint *u [[buffer(0)]],
#                 ..., ushort2 tp [[thread_position_in_threadgroup]],
#                 uint tid [[thread_index_in_threadgroup]]) {
#     ib.data(tp)->k = 0x5a5a0000u + tid;
#     simdgroup_barrier(mem_flags::mem_threadgroup);
#     u[tid]      = ib.data(tp)->k;
#     u[64 + tid] = ib.data(ushort2(0, 0))->k;
#   }
#
# 32 distinct values in the own-slot column and lane 0's value from every lane reading (0,0): the
# tile is a real shared addressable store indexed by thread position. The device buffer was filled
# with 0xdeadbeef first, so unwritten and written-zero are both distinguishable and neither appears.
#
# THE BARRIER IN THE SOURCE IS NOT IN THE PROGRAM. Apple's compiler elided it - the store is
# followed by a movimm and then the load, nothing between them. Within a simdgroup the accesses are
# already ordered, so a fence is not what makes the round trip work.
#
# THE API DETAIL: the pipeline must come from newComputePipelineStateWithDescriptor: on an
# MTLComputePipelineDescriptor. A pipeline obtained by function-name lookup does not carry what the
# driver needs to size the tile, and imageblockMemoryLengthForDimensions: then reports 768 bytes at
# 32x1. setImageblockWidth:height: on the encoder must match the threadgroup.
