# THE HARDWARE SPECIAL-REGISTER NUMBERING, which is not the MCRegister numbering and which
# nothing in Apple's tables exposes.
#
# read_sr's second operand is declared SIR32 and the authoring pass could never map it. It fits no
# base-plus-field in any of this project's three encoding domains - not the MCRegister id, not the
# slot form, not the index within the register class. It is a LOOKUP: the field holds a hardware
# special-register number that Apple's LLVM tables do not contain anywhere.
#
# The consecutive triples are what make it a numbering rather than a coincidence:
#
#     SR_TG_X_SIZE, Y, Z  ->  24, 25, 26        SR_LOCAL_X, Y  ->  36, 37
#     SR_LIBXDIM, YDIM    ->  44, 45            SR_PVQUAD, PVSIMD -> 20, 21
#
# In each case the MCRegister ids are NOT consecutive - SR_TG_X/Y/Z_SIZE are 55, 57, 59 - so the
# grouping comes from the hardware side, not from LLVM's alphabetical enum.
#
# THE FIELD DEPENDS ON THE ENCODED LENGTH and so does the numbering, which is why one table would
# have been wrong. Both are given below, each derived by requiring every bit to be constant across
# all instances that print the same register and to differ across registers, then checking the
# result is a bijection.
#
# WHAT THIS LICENSES: an authoring pass can emit read_sr for any register listed here by writing
# the number into the field. It must REFUSE a register not listed - the mapping is observed, not
# derived, and nothing here predicts the number of a register the corpus never read.
